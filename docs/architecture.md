# Architecture

Stow separates local state, GitHub reads, portable accessories, and the macOS interface.

| component | responsibility |
| --- | --- |
| `StowCore` | models, live Markdown storage and metadata index, Markdown styling ranges, repository colors, transfer codecs, paste parsing, attention classification, cache reconciliation, and update versions, policy, and settings |
| `StowGitHub` | GitHub CLI process transport, GraphQL decoding and pagination, refresh coordination, and lazy details |
| `StowUpdates` | the update check's one request: a release list read without cookies, credentials, or cache |
| `StowExtensionSDK` | plain versioned request, descriptor, configuration, and snapshot values plus `AccessoryProvider` |
| `StowExtensions` | provider registry, validation, timeout, cancellation, cache, and adapters |
| `StowSampleExtension` | optional synthetic provider with no network or host-state dependency |
| `StowCore` profiles | profile identity, the index, discovery, deletion to the Trash, and owner selection and grouping |
| `App` | AppKit lifecycle and panels, SwiftUI rendering, native text editing that applies those styling ranges, and observable orchestration |

## State and windows

`AppStore` owns the in-memory `AppState`. Board and detached windows reference one note by stable ID. A managed `<UUID>.md` file is the canonical Markdown source. The live `state.json` envelope uses disk schema version 2: `metadata` holds an `AppState` with empty note bodies, and `notesDirectoryName` names the validated managed notes directory. It retains links, frames, detached state, pins, dismissals, settings, board layout preferences, cached PRs, and accessory configuration.

`StateLock` holds an exclusive lock on a private file beside the index for the process lifetime, so only one process writes a state folder; the kernel releases it on exit or crash, and a second launch activates the running copy instead. `StateRepository` serializes persistence and uses coordinated file access with private temporary files and atomic replacement. The app serializes its persistence chain and debounces edits. An FSEvents watcher debounces external changes into a merge that compares disk sources with baselines and locally dirty notes. Detected conflicts preserve both versions as separate notes; clean external deletions remove notes while unsaved edits are preserved. Coordination cannot eliminate every race with an uncooperative editor.

Quit performs a final merged save before closing the writer. Source versions adopted by the repository but not yet acknowledged by the UI remain protected through subsequent saves and quit, so a stale UI snapshot cannot silently overwrite them. A failed flush lets the user keep the app open. Unsupported or damaged state blocks ordinary writes until repair or explicit backup recovery.

The first successful save of legacy JSON storage backs up the old index and migrates its note bodies to Markdown. Full restore writes all replacement sources into a new private `notes-<UUID>` folder, retains the previous folder and raw index, and atomically publishes the new index pointer. The host also saves a complete pre-restore backup. Watchers and file-reveal actions follow the current resolved directory; external editors must reopen files after restore.

The `.stowbackup` codec uses backup format version 1 and encodes a complete in-memory `AppState` snapshot, including note bodies, for explicit transfer and restore. Machine-local settings, the `gh` location and the GitHub switch, are written as defaults and keep this Mac's values on restore; restored accessories start disabled. `GHClient` launches only an absolute path named `gh` that resolves to a regular executable whose permission bits let neither its group nor other users write to it and set neither setuid nor setgid, outside the data folder both where it is and where it leads. It checks the path again before each launch and launches the file it checked. That envelope is separate from the metadata-only live disk index. The host synchronizes live edits before note exports or backup snapshots and refuses the transfer if synchronization fails. Markdown import validates all selected files before adding new note identities; exports are independent copies. See [portability](portability.md) and [privacy and recovery](privacy.md).

## Profiles

A profile is one state folder with its own `state.json`, notes folder, `.stow.lock`, and retained backups. The first profile is the data folder itself and is named "Stow"; others live in `profiles/<UUID>/`. Each profile folder can hold an `identity.json` with the profile's ID, name, color, and optional icon. `ProfileCatalog` finds profiles by looking at the folders, not at the index. It treats identity files and the index as untrusted input: sizes are limited, IDs must be UUIDs matching their folder, links and folders owned by another user are ignored, and names are sanitized.

`profiles.json` in the data folder is a small index of profile order, which profiles were open or hidden at quit, the most recently active profile, the IDs already seen, and app-wide display and update settings. It is created only when there is something to record. A corrupt or newer index is preserved, and **Reset profile list** moves it to a backup before writing a new one.

One process opens any number of profiles. `.stow-app.lock` is held for the process lifetime and decides whether a second launch hands over. Each open profile takes its own `.stow.lock`; if another process holds it, such as an older build using the first profile, that profile stays closed. A profile on a volume without locks, or whose folder can't be written or read or is a link, opens without its lock. Anything wrong at the lock path itself, such as a link, a folder, or another user's file there, keeps the profile closed, and Stow says so; at `.stow-app.lock`, Stow shows an alert and quits. `ProfileManager` owns the open sessions. Each `ProfileSession` has its own store, theme, GitHub client, refresh coordinator, accessory host, watcher, and windows, so nothing in one profile reads another's state. Profiles using the same `gh` location share one client and its rate-limit backoff. Hide, show, close, and switching act on a profile's windows together; hidden and closed profiles do not poll or run accessories.

Deleting a profile moves its folder to the Trash; the first profile is moved into `profiles/<id>/` first, with a journal so an interrupted move is finished or undone at the next launch. Stow never deletes profile data outright.

A profile folder Stow has not seen before opens with GitHub and accessories off and no saved `gh` location. Each profile remembers the login it last refreshed as. A refresh that answers as a different login is discarded and pauses the profile until the user chooses **Use X here**, which clears that profile's cached pull requests, details, and dismissals and keeps pins and notes.

Owners are the repository owners in pull request references, compared ignoring case. Each profile saves an owner selection that changes only what is visible; classification, warnings, pins, and refreshes are unaffected. Grouping and order are per-profile board layout settings. See the [profile design](profiles.md).

## GitHub reads

`GHProcessTransport` starts `gh api` directly for `github.com`, supplies JSON over standard input, and reads process output without blocking into bounded buffers. At the deadline or on cancellation, it kills `gh`'s process group while `gh` still runs, and closes the pipes. Once `gh` has exited, it signals nothing: when the output stays open, it stops reading a second later and uses the output `gh` wrote. It reuses the CLI’s existing authentication and sanitizes user-facing errors. Stow does not have a token store.

`GHClient` discovers the authenticated viewer, fetches authored and directly requested pull requests, resolves pins, paginates connections, and loads details on demand. Details fetch at most three pages per connection and keep at most 100 checks and 100 reviews, preferring checks that need attention, so a very large pull request cannot bloat the saved index. The last three commits come with the first page of reviews. A new installation leaves GitHub off until the user opts in. `RefreshCoordinator` coalesces overlapping refreshes. The app refreshes on activation and periodically while GitHub is enabled.

Classification distinguishes observed facts from incomplete readiness. Conflicts, requested changes, failing checks, direct review requests, and complete merge readiness can need attention. Draft and terminal states override readiness. Unknown checks, mergeability, review data, or incomplete pagination cannot establish “Ready to merge.” “Behind base branch” is informational. A green outline marks an open, approved pull request only while its data is fresh; a purple one marks a merged pull request, in a purple that follows the theme's color scheme and is never saved. Pins preserve watched cards; dismissals hide cards without deleting notes. Unpinned merged and closed cards sit in a Merged group under Waiting, wherever Waiting is in the order. It isn't a saved section: it starts collapsed each launch, keeps its state only in memory, and hides when empty. Pinned ones stay in Waiting. An unpinned merged or closed card leaves at the first refresh after the profile's keep time (none, an hour, a day by default, or a week) has passed since Stow first saw it so, even if that refresh is incomplete; a pinned one never expires. Choosing a shorter keep time in Settings removes cards already past it at once, and choosing a longer one again doesn't bring them back; notes are never touched. Lists return only open pull requests, so an unpinned merged or closed card a result brings without one already on the board comes from a repeated or stale result and is ignored: applying one result twice, or a result that lands after a shorter keep time, never moves a card or brings back one that left. The keep time is an optional `state.json` key that falls back to a day; 0.3.0 drops it when it saves.

## Update check

`ReleaseFeed` in `StowUpdates` makes the one request Stow sends without `gh`, and only after the person turns on Settings → Updates or chooses **Check for updates…**. It uses an ephemeral `URLSession` with no cookies, credentials, or cache, fixed headers, and a 30-second limit, and reads at most 1 MiB. Everything else is plain values in `StowCore`. A `ReleaseSource`, Stow's by default, names the release list and the one page each release may link to: `https://github.com/byanthny/stow/releases/tag/` and that release's tag. An `UpdatePolicy` decides when a check is due and which release to offer: release tags compare as Semantic Versioning, and pre-releases count only until a check has found a stable release. `UpdateSettings.record` turns a check's result into what the board offers; a failed check changes nothing, so the earlier release stays offered and the next check stays due. `UpdateMonitor` in the app runs one check at a time, whenever asked and, while the setting is on, at launch and on an hourly wake-up once a day has passed since the last check that worked or the clock went back. A failed check is therefore tried again within the hour. It keeps the setting and the last result in `profiles.json`, and Settings → Updates says when they can't be saved; the board shows a notice until it is dismissed or that version runs. Nothing downloads.

Older Stow versions don't know the update settings, so one that rewrites `profiles.json` drops them, and a damaged value reads as off. Either way, checks stay off until turned on again.

## Dependency direction

The SDK depends only on Foundation. Core may store SDK configuration values, but providers receive only their explicit request. The host owns placement and rendering. The app links the modules; module tests do not depend on the app.

The JSON adapter exercises a serialization boundary in-process. It does not launch an executable, isolate code, or promise a stable binary ABI. A later host may carry the same values over a process transport without introducing macOS view types into the contract.
